# 系统设计

## 1. 要解决的问题

大模型可以概括简历，但“给出一个分数”不等于形成可信的招聘流程。本项目把重点放在三个问题：判断依据能否回到原文、HR 是否保留最终决定权、每次变化能否追溯。

生活类比：它更像带页码的审阅意见，而不是替老师打最终分——每条意见都要指出原文位置，老师仍可修改结论，并留下修改记录。

## 2. 数据流

1. 后端预检 CSV，并让用户明确选择岗位与本轮候选人数。
2. 模型从完整 JD 提取标准草稿，HR 确认后固化为版本。
3. 每份简历只把完整 JD、确认标准、`resume_id` 与原始正文送入模型端口。
4. 后端验证引用是否存在于当前简历，计算匹配程度与证据可靠度。
5. AI 建议进入推荐、待定或暂不建议层；HR 采纳或推翻。
6. 导入、模型输出、失败和复核都追加到审计记录，历史不覆盖。

## 3. 模块职责

| 模块 | 责任 |
|---|---|
| `src/backend/main.py` | HTTP 路由、请求标识、响应契约和错误映射 |
| `src/backend/application/` | 创建任务、标准版本、分析、复核等业务用例 |
| `src/backend/domain/` | 证据校验、分层、年限判断等纯规则 |
| `src/backend/ports.py` | 定义模型与存储接口，隔离外部实现 |
| `src/backend/llm.py` | 真实 OpenAI 兼容模型适配器 |
| `src/backend/demo_llm.py` | 确定性的离线流程演示适配器 |
| `src/backend/storage.py` | JSON/JSONL 文件存储与追加事件 |
| `src/frontend/` | 四步 HR 操作界面与证据账本 |

## 4. 关键判断

- 不把 CSV 中已有评分或录用标签当作生产输入，避免“答案泄漏”。
- 不把模型自报置信度当作事实；证据必须能在当前简历定位。
- 不用单一总分直接决定去留；匹配与证据可靠度分开保存。
- 修改标准后旧结果失效，防止不同标准下的结果被混用。
- 批量处理允许单份失败，并保持“已处理 = 成功 + 失败”的数量守恒。
- 文件存储保持单 worker；若进入生产，应切换到带事务和并发控制的数据库。

## 5. 离线演示与真实模型的关系

两种实现都遵守 `LLMProvider`。离线模式只替换外部模型这一环，任务、标准版本、证据校验、分层、复核和审计仍走真实代码。因此它证明的是系统闭环可运行，不证明大模型质量。
